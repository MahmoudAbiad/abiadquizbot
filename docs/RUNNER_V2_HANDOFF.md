## 2) T1 — تسريب الجواب الصحيح

**المشكلة.** في `build_questions` (`services/runner_core.py`) الخيار الصحيح دايماً موجود، والخياران الخاطئان بيتغيروا عشوائياً مع كل جولة (`rng.sample(wrong, 2)`). لاعب بيعمل `/start` ثم `/question` مرتين أو ثلاثة، وبيقارن الخيارات: اللي بيتكرر دايماً هو الصحيح. حد `/start` هو 4/دقيقة وهاد كافي.

**المطلوب.**
- اختيار الخيارين الخاطئين يصير **حتمياً لكل (user_id, quiz_id, question_key)**:
  ```python
  seed = hmac_sha256(secret, f"{user_id}:{quiz_id}:{key}")   # secret = RUNNER_SIGNING_SECRET أو bot.token كاحتياط
  wrong_pick = random.Random(int.from_bytes(seed, "big")).sample(wrong, 2)
  ```
- ترتيب الخيارات الثلاثة (shuffle) يضل عشوائي لكل جولة (`SystemRandom`) — هاد ما بيسرّب شي.
- عدّل التوقيع بشكل متوافق مع الاختبارات الحالية: `build_questions(questions, settings=None, rng=None, *, user_id=None, quiz_id=None, seed_secret=None)`. إذا ما انمرّرت `user_id/quiz_id/seed_secret` (مثل `/config`) يضل السلوك القديم.
- مرّر القيم من `/start` فقط (`services/runner_api.py`).
- سؤال بـ 3 خيارات بالضبط: ما يتغير شي.

**معيار القبول (اختبارات):**
- 10 جولات متتالية لنفس (user, quiz, question): مجموعة معرّفات الخيارات الظاهرة **متطابقة** دايماً، والصحيح موجود.
- مستخدمان مختلفان: الصحيح موجود عند الاثنين، ومجموعتا الخاطئين **قد** تختلفان.
- مجموعة الخيارات لا تتغير لو تغيّر ترتيبها.

## 3) T2 — رسم الاختبار كله مسبقاً + كاش أسبوع + السيرفر الثاني

### 3.1 الهدف (قرار صاحب المشروع)
- لما اللاعب يبدأ اللعب (`/start`) تبدأ عملية رسم **كل** صور الاختبار بالخلفية فوراً، بحيث الأسئلة ما تتأخر عليه.
- الصور تنحفظ كاش **صالح لمدة أسبوع**، فلو طالب ثاني لعب نفس الاختبار تكون الصور جاهزة.
- **نستفيد من السيرفر الثاني (render worker) إذا كان مفعّلاً**، وإذا لا: السلوك المحلي مع حدود صارمة.

### 3.2 حقائق عن السيرفر الثاني (تحقّق منها بالكود قبل ما تبني عليها)
- `render_game_image_async` (في `services/image_quiz_renderer.py`) بتمر أصلاً على `render_question_image_async` → `offload.remote_render_image` → السيرفر الثاني إذا `offload.ENABLED`، وإلا محلياً بـ `RENDER_SEMAPHORE` (حده 3 ومشترك مع باقي البوت).
- لكن `runner_api.py` فيه `_render_gate = asyncio.Semaphore(1)` عالمي لكل المستخدمين، فيسلسل كل الرسم حتى لو السيرفر الثاني متاح. **لازم يُستبدل.**
- حدود السيرفر الثاني (`render_worker.py`): `WORKER_CONCURRENCY` الافتراضي 2 (أقصى 2)، `WORKER_MAX_QUEUE` الافتراضي 8، `WORKER_QUEUE_WAIT_SECONDS` 40. من جهة الرئيسي: `OFFLOAD_REMOTE_CONCURRENCY` الافتراضي 8، وقاطع دائرة (3 فشل متتالي → 30 ثانية توقف).
- ⚠️ `OFFLOAD_FALLBACK_LOCAL` افتراضياً `1`: إذا السيرفر الثاني رفض أو فشل، الرسم **يرجع للسيرفر الرئيسي**. رسم كويز كامل بالخلفية بهالطريقة ممكن يضغط ذاكرة الـ 512MB. لازم نمنعه (3.5).
- `offload.is_active()` تقول إذا السيرفر الثاني مفعّل وقاطع الدائرة مسموح. استخدمها لتحديد الوضع.
- لا تغيّر `render_worker.py` إلا إذا لزم فعلاً (تحقق إن `_game_part` يُعالَج بنفس الطريقة محلياً وعلى الـ worker بنفس الناتج).

### 3.3 تغييرات قاعدة البيانات — `db/migrations/0018_runner_image_cache.sql` (+ `_rollback.sql` بنفس نمط الملفات السابقة)
```sql
begin;
alter table public.runner_images add column if not exists created_at timestamptz not null default now();
alter table public.runner_images add column if not exists expires_at timestamptz not null default now() + interval '7 days';
create index if not exists runner_images_expiry on public.runner_images(expires_at);
create index if not exists runner_rounds_retention on public.runner_rounds(expires_at);
commit;
```
المفتاح الأساسي يبقى `(quiz_id, question_key, part)`. الصف يُعتبر **ضربة كاش فقط إذا `expires_at > now()`**.

### 3.4 المكوّنات
**(أ) `get_or_render_image(quiz_id, question, part, *, background=False)`** (بدل `game_image` الحالية):
1. اقرأ الصف: إذا موجود وصالح (`expires_at > now()`) رجّع الـ URL.
2. منع الرسم المكرر: خريطة `_inflight[(quiz_id,key,part)] -> Future` داخل العملية + قفل Redis `runner:img:{quiz}:{key}:{part}` (`SET NX EX 120`) للتعدد بين العمليات. إذا القفل عند غيرك: انتظر وانظر لجدول DB كل ~300ms لحد 15 ثانية.
3. ارسم → ارفع إلى المسار الثابت `runner/{quiz_id}/{key}/{part}.png` → upsert للصف مع `created_at=now()` و`expires_at=now()+RUNNER_IMAGE_CACHE_DAYS` (افتراضي 7 أيام).
4. تحقّق من `upload_quiz_question_image` (في `helpers/supabase_helper/quiz_images.py`): هل يسمح بالكتابة فوق ملف موجود (upsert)؟ إذا لا، عدّله، لأن التجديد بعد الانتهاء يكتب على نفس المسار.

**(ب) `prewarm_quiz_images(quiz_id, questions)`** — مهمة خلفية (استخدم `spawn` الموجود بالمشروع، ولا تنتظرها داخل الطلب أبداً):
- تُطلق من `/start` بعد إنشاء الجولة، و`/start` يرجع فوراً.
- جولة واحدة فقط لكل كويز: قفل Redis `runner:prewarm:{quiz_id}` (TTL 15 دقيقة، يُحرَّر عند الانتهاء). إذا في مهمة شغّالة لنفس الكويز: لا تبدأ ثانية.
- الترتيب: حسب ترتيب الأسئلة بالجولة، من السؤال الأول.
- **الأجزاء المرسومة لكل سؤال «صوري»** (`is_math` أو `table` أو `matrices` أو فيه `$`): `question` + **كل** الخيارات (`part` = رقم الخيار الأصلي). نرسم كل الخيارات (وليس الثلاثة المختارة فقط) لأن الخيارات المعروضة تختلف من طالب لطالب بعد T1، وهيك الكاش يخدم الكل.
- حدود التوازي:
  - السيرفر الثاني فعّال (`offload.is_active()`): `RUNNER_PREWARM_CONCURRENCY_REMOTE` (افتراضي **4**، ولا تتجاوز `OFFLOAD_REMOTE_CONCURRENCY`، وتذكّر أن الـ worker يستوعب 2 تنفيذ + 8 طابور).
  - بدون سيرفر ثاني: `RUNNER_PREWARM_CONCURRENCY_LOCAL` (افتراضي **1**)، ومع `release_memory_to_os()` بعد كل صورة (الدالة المحلية الموجودة بتعملها أصلاً)، وسيمافور خاص بالـ prewarm منفصل عن طلبات اللاعب حتى ما يجوّع الرسم المطلوب فوراً.
- **ممنوع الرجوع للرسم المحلي أثناء الـ prewarm إذا السيرفر الثاني مفعّل لكنه فشل**: أضف وسيط اختياري (مثلاً `allow_local_fallback: bool = True`) لمسار `remote_render_image`/`render_question_image_async`، والـ prewarm يمرّره `False`. عند الفشل: أعد المحاولة بعد backoff (30 ثانية، حتى 3 مرات) ثم اترك الصورة للرسم عند الطلب. طلبات اللاعب المباشرة (`/question`) تحتفظ بالسلوك الحالي (fallback محلي) لأن في طالب ينتظر.
- فشل صورة واحدة لا يوقف المهمة. اكتب سطر log ملخّص واحد بالنهاية (عدد المرسوم/المخزّن مسبقاً/الفاشل، والوضع: remote/local).
- إذا `RUNNER_PREWARM_ENABLED=0` تتعطل المهمة وتبقى الصور تُرسم عند الطلب.

**(ج) مسار الطلب `/question`:**
- استبدل `_render_gate` وكل الاستدعاءات المتسلسلة: اطلب صور السؤال (السؤال + الثلاثة المختارة) بـ `asyncio.gather`، محكومة بسيمافور ديناميكي: `offload.REMOTE_CONCURRENCY` إذا السيرفر الثاني فعّال، وإلا `2` (أقل من `BASE_LOCAL_RENDER_LIMIT`).
- هاد المسار له أولوية على الـ prewarm. إذا الصورة قيد الرسم بالـ prewarm: انتظرها (3.4-أ-2) بدل أن ترسمها مرة ثانية.
- سقف انتظار ~25 ثانية، بعده خطأ بـ `code="image_unavailable"` (قسم 4) والواجهة تعرض «إعادة المحاولة».

**(د) تلميح تحميل مسبق للمتصفح (اختياري ومُوصى به):** رد `/answer` (إذا الجولة مستمرة) يرجع `prefetch: [urls…]` لصور السؤال التالي **إن كانت جاهزة بالكاش** (لا ترسم شي لأجلها). الواجهة تعمل `new Image().src` لتسخين المتصفح. ما فيه تسريب جديد: نصوص كل الأسئلة أصلاً ظاهرة عبر `/config`.

### 3.5 معايير القبول لـ T2
- أول لاعب على كويز رياضيات: `/start` يرجع بأقل من ثانية، والسؤال الأول يظهر بدون تأخير ملحوظ، والأسئلة اللاحقة جاهزة تقريباً قبل ما يوصلها.
- لاعب ثاني على نفس الكويز خلال أسبوع: **صفر** عمليات رسم (تحقق بعدّاد/لوغ).
- بعد 7 أيام: الصف يُعتبر منتهياً ويُعاد الرسم ويتجدد `expires_at`.
- طالبان يبدآن نفس الكويز بنفس اللحظة: مهمة prewarm واحدة فقط، وصورة واحدة لا تُرسم مرتين.
- السيرفر الثاني مفعّل ومعطّل (محاكاة فشل): الـ prewarm لا يرسم محلياً أبداً ويعيد المحاولة بـ backoff؛ طلب اللاعب المباشر يرجع للمحلي.
- السيرفر الثاني غير مفعّل: التوازي = 1 والذاكرة مستقرة.
- اختبار بالـ mocks لكل ما فوق (لا شبكة حقيقية).

## 4) T4 — متانة الواجهة ورموز الأخطاء

**المشاكل الحالية** (`webapp/runner/game.js` + `runner_api.py`):
- إذا `/question` رجّع 409/410 (الجولة انتهت/انتهت صلاحيتها) الواجهة تدخل حالة `retry` وزرّها يعيد نفس الطلب للأبد. ما فيه طريق لجولة جديدة.
- `pagehide` يستدعي `cleanup()` اللي يعلّم الجولة `abandoned` ويوقف حلقة الرسم نهائياً (`disposed=true` + `{once:true}`). على الموبايل تبديل التطبيق ممكن يطلق `pagehide`، فالطالب يرجع لجولة ميتة.

**المطلوب:**
1. **رموز أخطاء مقروءة آلياً** من السيرفر: أضف `code` لكل خطأ (مثلاً عبر `detail={"message":…, "code":…}` أو handler يرجع JSON موحّد). الرموز: `round_over`، `round_expired`، `stale_version`، `quiz_changed`، `rate_limited`، `image_unavailable`، `auth`. عدّل `api()` بالواجهة لتتعامل مع الشكلين.
2. **`/question` يتجاهل `version` القادم من العميل** ويرجع السؤال الحالي دائماً (هو أصلاً idempotent، وحماية التزامن الحقيقية هي compare-and-set بـ `/answer`). هيك ما ينتج `stale_version` من `/question`.
3. **الواجهة:**
   - `round_over` / `round_expired` ⇒ شاشة واضحة + زر «ابدأ جولة جديدة» (يستدعي `start`).
   - `stale_version` عند `/answer` ⇒ أعد جلب `/question` تلقائياً بدون إزعاج المستخدم.
   - أخطاء الشبكة ⇒ زر «إعادة المحاولة» لعدة مرات، وبعدها عرض «ابدأ جولة جديدة».
   - **لا تعلّم الجولة `abandoned` عند `pagehide`**. عند `pagehide`/`visibilitychange` فقط: إيقاف مؤقت للرسم والصوت. التعليم `abandoned` يصير فقط بزر الخروج الصريح (`sendBeacon`/`keepalive`) أو بانتهاء الصلاحية على السيرفر أو ببدء جولة جديدة.
   - أضف معالج `pageshow`: إذا `event.persisted` (bfcache) أعد تشغيل حلقة الرسم (`disposed=false`) ثم زامن الحالة (`/question` إذا في جولة، وإلا `config`). احذف `{once:true}` والإيقاف الدائم.
4. إذا رجع الطالب بعد انتهاء وقت السؤال (بالخلفية)، المؤقت على السيرفر كان شغّال: اعرض رسالة «انتهى وقت السؤال» بدل لغز صامت (السلوك يبقى timeout عادي).

**معيار القبول:** اختبارات (API + اختبار المتصفح بالـ mocks) لـ: 409/410 ⇒ ظهور زر جولة جديدة وعمله، `pagehide` لا يعلّم `abandoned`، `pageshow(persisted)` يعيد الحياة، `stale_version` يُعاد تلقائياً.

## 5) T3 — المؤقت يبدأ عند ظهور السؤال فعلاً

**المشكلة.** `/question` يثبّت `issued_at` على السيرفر **قبل** ما الصور توصل/تنفكّ بالمتصفح، والواجهة تحسب `deadline` بعد وصول الرد (`sentAt`) فتضيع أزمنة الشبكة وتحميل الصور. السماح الحالي 2 ثانية فقط.

**المطلوب (بروتوكول `ready`):**
1. `/question` يرجع السؤال **بدون** تشغيل المؤقت (لا يضبط `issued_at`). إذا `issued_at` مضبوط مسبقاً (إعادة تحميل وسط السؤال) يرجع `started=true` و`remaining_seconds`.
2. نقطة جديدة `POST /api/runner/ready` (نفس `RoundRequest`): تضبط `issued_at=now` بـ compare-and-set على `version` (`issued_at is null` فقط، idempotent: إذا مضبوط ترجع نفس `remaining_seconds`).
3. الواجهة: تحمّل صور السؤال والخيارات بشكل **مخفي** وتنتظر `img.decode()` (مع مهلة معقولة)، ثم تستدعي `/ready`، ثم تُظهر السؤال. `deadline = tReadySent + seconds*1000` (لحظة **إرسال** الطلب وليس وصول الرد — محافظ لصالح السيرفر، ولا نمدّ الوقت بزمن الشبكة).
4. `answer_transition` يرفض أصلاً إذا `issued_at is None` («السؤال غير نشط») — حافظ على ذلك.
5. حدّث `tests/runner_browser.cjs` ليحاكي `ready`.

**ملاحظة مخاطرة مقبولة:** نص السؤال/روابط الصور تصل للعميل قبل `/ready` (ضرورية للتحميل المسبق)؛ يعني غشاش تقني ممكن يقرأ بدون مؤقت. هاد مقبول حالياً لأن النقاط معرفية شخصية، ونصوص الأسئلة أصلاً متاحة عبر `/config`. وثّق هالنقطة بـ `RUNNER_MVP.md`، ولو ربطوها يوماً بليدربورد/جوائز لازم نعيد التقييم.

## 6) T5 — Retention: تنظيف الجولات والصور

**المشكلة.** `runner_rounds` تخزّن لقطة كاملة لكل الأسئلة (لحد 300 مع `source` كامل) عند كل `/start` بدون أي تنظيف. صور `runner/{quiz_id}/…` بالـ bucket `quiz-images` تضل يتيمة عند حذف الكويز (الصفوف تنحذف cascade لكن الملفات لا). ولا يوجد حالياً helper لحذف ملفات التخزين بـ `quiz_images.py`.

**المطلوب:**
1. helper جديد بـ `helpers/supabase_helper/quiz_images.py`: `delete_runner_images(paths: list[str])` (دفعات، best-effort) و`delete_runner_prefix(quiz_id)` (list + remove للمسار `runner/{quiz_id}/`).
2. حلقة `runner_cleanup_loop` (كل ساعة تقريباً):
   - **الصور المنتهية:** اجلب صفوف `runner_images` بـ `expires_at < now()` (دفعات ≤200)، احذف ملفاتها من التخزين **أولاً**، ثم احذف الصفوف (لو فشل الحذف من التخزين تتكرر المحاولة بالدورة التالية).
   - **الجولات القديمة:** احذف من `runner_rounds` ما `coalesce(finished_at, expires_at) < now() - interval '7 days'` (دفعات ≤500).
3. **شغّلها بالوضعين:** `webhook_server.py` (lifespan) **و**`main.py` (polling)، مثل حلقات التحديات. لا تضعها داخل `scheduled_cleanup_loop` لأن ذاك التعليق بـ `main.py` يقول إنه ما يشتغل بوضع polling.
4. **عند حذف كويز** (`handlers/quiz_delete.py`): استدعِ `delete_runner_prefix(quiz_id)` best-effort بعد الحذف الناجح (بعد الـ cascade ما بقي صفوف تدلّ على الملفات).
5. **لقطة الجولة المضغوطة (موصى به بعد ما يشتغل التنظيف):** خزّن فقط ما يلزم (`source_index`، `key`، الخيارات المختارة `[ids]`، `correct_id`، `seconds`، نص السؤال/الخيارات/الشرح الضروري لرد `/answer`)، واترك `table/matrices/ai_*` وغيرها خارج اللقطة (الصور تُرسم أصلاً من الكويز عند الكاش). الهدف تخفيض حجم الصف للثلث تقريباً. لو أصبح هالتغيير معقداً أجّله وانتهِ بالتنظيف فقط.

**معيار القبول:** اختبارات بالـ doubles: الصور المنتهية تُحذف من التخزين والجدول بالترتيب الصحيح، فشل الحذف من التخزين لا يحذف الصف، الجولات الأقدم من 7 أيام تُحذف والأحدث لا، حذف الكويز يستدعي حذف المسار.

## 7) T6 — تجربة اللعب

### 7.1 العملات ما تختفي بعد الجمع (خطأ)
- المكان: `updateWorld` + حلقة الرسم في `game.js`. عند الالتقاط يُضبط `o.done=true` وتزيد العملات، لكن الكائن يبقى بالمصفوفة ويُرسَم كأنه ما انجمع حتى `z>1.1`.
- المطلوب: عند الالتقاط `o.taken=true` ⇒ **لا يُرسم بعدها**، مع تأثير خاطف (~220ms): تكبير + تلاشي + حركة صغيرة باتجاه عدّاد العملات + جسيمات قليلة. العملات اللي ما انجمعت تمر خلف اللاعب وتتلاشى تدريجياً (alpha يتناقص بين `z≈0.85` و`z≈1.0`) بدل ما تبقى واضحة.
- العوائق: عند الاصطدام تتحطم/تختفي بتأثير بدل ما تبقى (والقفز فوقها يبقى كما هو).
- يُفضّل نقل منطق التحديث/الالتقاط إلى `webapp/runner/world.js` كدوال نقية (بدون DOM) لتسهيل الاختبار بـ node.

### 7.2 الأسئلة تظهر فجأة → «بوابات الإجابة» (اقتراح صاحب المشروع + تحسين)
**فكرة صاحب المشروع:** السؤال يظهر كـ 3 عوائق، والجواب الصحيح يُزيل عائقاً.
**التصميم المعتمد (نسخة محسّنة من نفس الفكرة):**

مراحل السؤال بدل التجمّد المفاجئ:
1. **RUN** (كما هو، ~8 ثواني): عملات وعوائق عادية.
2. **APPROACH** (~1.5 ثانية): توقف توليد العملات/العوائق، والعالم يتباطأ بسلاسة (easing من 1.0 إلى ~0.35). تظهر **3 بوابات** من الأفق (واحدة بكل مسار) وتقترب حتى `z≈0.62`، ولوحة السؤال تنزلق من الأعلى. تُجهَّز الصور بالتوازي مع هذه المرحلة.
3. **DECIDE:** البوابات ثابتة، اللاعب يتحرك بمكانه (slow-mo)، يختار المسار بالسحب أو بالنقر على بوابة، ويثبّت بزر «ثبّت الإجابة». المؤقت يبدأ من `/ready` (T3). الانتهاء بدون تثبيت = timeout كما هو.
4. **RESOLVE** (بعد رد `/answer`): اندفاع قصير نحو البوابات (~0.5 ثانية).
   - **صحيحة:** بوابة اللاعب **تنكسر/تذوب** (جسيمات + `correct.mp3`) ويعبر منها، وتنفجر عملات، والبوابتان الأخريان تتلاشيان.
   - **خاطئة:** يصطدم بالبوابة الخاطئة وتبقى صلبة (اهتزاز + `near.mp3` + haptic) ويقترب الشرطي (منطق الفرص الحالي)، و**تضيء البوابة الصحيحة بالأخضر وتنفتح** ليشوف الطالب الجواب.
   - **انتهاء الوقت:** كل البوابات مغلقة والصحيحة تضيء.
   - بعدها لوحة الشرح الحالية (`feedback`).

التنفيذ:
- كل بوابة تحمل محتوى الخيار: صورة (رياضيات) أو نص عربي. استخدم **عناصر DOM** (`<button>` بـ `aria-label` = نص الخيار) موضوعة فوق الـ canvas بنفس معادلة الإسقاط `point(lane, z)`، والـ canvas يرسم الإطار والأعمدة والتوهج. النص العربي يلتفّ RTL ويتقلّص ليلائم الحجم (حد أدنى للخط ~14px).
- **رجوع تلقائي (fallback):** إذا الخيار طويل (مثلاً > ~60 حرفاً) أو الصورة أعلى من ~25% من ارتفاع الشاشة، استخدم اللوحة السفلية الحالية (`#choices`) لهالسؤال.
- احترم `prefers-reduced-motion`: بدون easing/جسيمات، فقط إظهار/تلاشي.
- لا تغيّر عقد الـ API (غير `/ready`)، ولا منطق النقاط/الفرص.
- حافظ على الأداء: DPR حتى 2، كائنات محدودة، delta-time، تحديث تموضع الـ DOM فقط أثناء APPROACH/RESOLVE.
- حدّث `tests/runner_browser.cjs` (الإجابة، البوابات، الوصول للتغذية الراجعة)، وتحقق بصرياً بحجم 390×844 (لقطات شاشة) وبدون overflow أفقي وبدون أخطاء JS.

## 10) خارج النطاق (لا تنفّذ إلا إذا طُلب)

ملاحظات من المراجعة متوسطة/منخفضة الأولوية، مذكورة فقط لتعرف السياق:
- `build_questions` يرفض الكويز كله إذا سؤال واحد فيه أقل من 3 خيارات (مثل صح/خطأ)؛ الأفضل استبعاد الأسئلة غير المؤهلة وإظهار «استُبعد X من Y».
- `/start` يلغي كل جولات المستخدم الجارية (ليس فقط لنفس الكويز) وبدون idempotency.
- `access()` يجلب `select('*')` من `quizzes` (كل `quiz_data`) عند كل `/question` و`/answer`.
- `/estimate`: حالة `running` تعلق بعد crash (يلزم انتهاء مهلة ~3 دقائق)، و`valid_time` يرفض الدفعة كلها إذا قيمة واحدة خارج 10–300 (الأفضل clamp).
- زر «العب» على اختبار نصي حالي يحفظه بالـ DB فوراً بلا rate limit، وبعض رسائل `ValueError` (مثل `UUID`) قد تظهر للمستخدم بالإنجليزية.
- رابط الإطلاق موقّع بتوكن البوت ويوضع بالـ query string؛ و`incr` ثم `expire` للـ rate limit غير ذريين.
- تصميم: عدد الفرص الافتراضي 1، واصطدامان بعوائق (شكلية) ينهيان الجولة ويسجّلانها `abandoned`.
- اختيار صور الخيارات: لو الخيار نص عادي بلا رياضيات ممكن يُعرض كنص بدل صورة (يقلّل الصور كثيراً).

## 11) قرارات اتُّخذت وقرارات مفتوحة

**مُتَّفَق عليها:** كاش الصور أسبوع واحد؛ بدء الرسم المسبق عند `/start`؛ الاستفادة من السيرفر الثاني إذا كان مفعّلاً؛ العملات تختفي بعد الجمع؛ الأسئلة كبوابات/عوائق تُزال بالجواب الصحيح؛ المشاكل الخمس المهمة (T1–T5) ضمن النطاق.

**افتراضات اخترتُها (غيّرها فقط إذا طلب صاحب المشروع):**

- رسم كل خيارات السؤال الصوري (وليس الثلاثة المختارة فقط) لتعظيم ضربات الكاش بين الطلاب.
- الإطلاق عند `/start` وليس عند فتح الـ Mini App (`/config`)، حتى ما نرسم لاختبارات ما بدأ أحد لعبها.

**عند الانتهاء:** حدّث `docs/RUNNER_MVP.md` (البروتوكول الجديد، الكاش، الـ retention، المتغيرات، المخاطر المقبولة)، واكتب ملخصاً بنتائج الاختبارات الفعلية (كم نجح/تخطّى/فشل ولماذا)، ولا تدّعِ نتائج ما شغّلتها. لا تعمل merge إلى الإنتاج؛ نشر test مسموح وفق التفويض الحالي.
